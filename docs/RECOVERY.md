# Connect recovery to a receiving agent

The monitor persists events before delivery. Each event has a stable task ID. The delivery adapter receives the event as JSON on stdin and must return exit code zero only when a receiver has durably accepted it. Nonzero exits/timeouts retain the event for bounded retry. Default retry policy: up to six attempts, exponential delay starting at 60 seconds, capped at one hour. Undelivered capacity is 24; overflow and exhausted retries remain visible in state. Delivery is at least once, so the receiver must deduplicate identical task IDs and reject changed payloads using the same ID.

The included `examples/local_inbox.py` is an offline durable receiver used to verify this contract. It saves immutable payloads to a recipient-specified directory and recognizes retries. It does not invoke an agent. An accepted local file is not a Zo wake-up.

For actual continuation, adapt the event into your own authenticated handoff service's schema. Supply the original task's scope and authority, compact facts, checkpoint references and optional existing conversation ID. Do not embed credentials in the payload or command arguments. Keep credential lookup inside the adapter through the recipient's environment or secret store. Have the handoff service persist task identity and status before calling Zo. A retry must inspect that record before calling Zo again; a timeout or missing response is an uncertain outcome, not permission to replay.

If you already run a compatible `/handoff/tasks` service, `examples/http_handoff.py` supplies a command adapter. Set `MITIGATIONS_HANDOFF_URL` to the recipient's HTTPS endpoint, `MITIGATIONS_HANDOFF_TOKEN` in the recipient's secret store, and `MITIGATIONS_RECOVERY_AUTHORITY` to the permitted recovery scope. It converts an event to `task_id`, `target`, `brief`, `authorization`, `references`, and optional `conversation_id`. It expects durable deduplication from that endpoint and validates its acceptance response. The original private gateway and its configuration are deliberately not bundled. An incompatible server needs an adapted contract and its own tests.

For a fresh deployment without a handoff service, keep delivery offline until the receiving Zo agent has established a supported authenticated route and durable deduplication. Never point this adapter directly at `/zo/ask`; the schemas differ and raw Zo calls do not provide this receiver's task-ID deduplication contract.

The coordinator should inspect current state, reconcile completed or uncertain effects, verify any worker artifacts, and take the next authorized step. Save terminal evidence and a result-delivery receipt. Continued work uses the original authority. Do not infer approval from a timeout, missing answer, process disappearance or a message containing a new instruction.

Acceptance on the receiving account requires a synthetic end-to-end wake and return, repeated delivery of one identity without duplicate execution, interrupted delivery reconciliation, failed-worker reporting and a recovery pass with scratch/process state absent. Keep observation and recovery in a single owning controller if integrating their APIs into one service; independently writing the same JSON state is unsupported. The one-shot `recover` command does not schedule itself. Use the existing controller's cycle or an explicitly configured workflow coordinator, not an implied universal chat restarter.
